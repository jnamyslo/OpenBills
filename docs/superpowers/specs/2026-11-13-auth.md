# Lokale Authentifizierung, Nutzerverwaltung und Audit-Log

Stand: 2026-11-13

## Ziel

Auth wandert von extern (NPM Forward-Auth → Authentik) in OpenBills selbst. Neue Kunden-Instanzen sind ohne externes IdP nutzbar: Beim Deploy entsteht ein Onboarding-Link, über den der Kunde seinen ersten Admin anlegt. Der Betreiber hat einen eigenen, für den Kunden als „Support-Zugang des Betreibers“ gekennzeichneten Zugang. Alle sicherheitsrelevanten und fachlichen Änderungen werden im Audit-Log protokolliert.

Löst die Annahme „Auth unverändert (Authentik + NPM Forward-Auth)“ aus `2026-11-13-plan-tiers.md` ab.

## Entscheidungen

- **Rollen:** `admin` und `user`. Erster Nutzer über Onboarding = `admin`. Admin legt weitere Nutzer an (Rolle wählbar).
- **Support-Zugang (Betreiber):** Rolle `admin` + Flag `is_operator`. Nicht in der normalen Nutzerliste, aber in der Nutzerverwaltung als fester Hinweis „Support-Zugang des Betreibers (aktiv)“ inkl. letztem Login sichtbar. Kunde kann ihn nicht bearbeiten oder löschen. Muss im AV-Vertrag/den AGB offengelegt sein.
- **Support-Zugang-Credentials:** Werden vom Skript erzeugt und **einmal angezeigt**. In der DB nur Hash. Nichts davon in `.env*`-Dateien.
- **2FA (TOTP):** Optional für alle, inkl. Kunden-Admins und Support-Zugang. Für Admins in der UI deutlich empfohlen (Hinweisbanner bis aktiviert). 10 Recovery-Codes (Einmalnutzung).
- **Passwort-Reset:** Per Mail, Link 1 h gültig, einmalig. Ohne funktionierende SMTP-Konfiguration kann ein Admin für einen Nutzer einen Reset-Link erzeugen und selbst weitergeben.
- **Einladung neuer Nutzer:** Admin erzeugt Einladungslink (48 h, einmalig), Nutzer setzt Passwort selbst. Admin kennt Passwort nie. Versand per Mail, falls SMTP konfiguriert, sonst Link kopieren.
- **Sessions:** Serverseitig in Postgres (überleben Restarts), Cookie `httpOnly`, `Secure` (wenn `PUBLIC_URL` https), `SameSite=Lax`, Pfad `/`. Idle-Timeout 12 h, absolut 30 Tage. Kein JWT.
- **Öffentliche URL:** `PUBLIC_URL` in `.env.backend.<name>`, beim Deploy abgefragt. Basis für alle Links und für den Origin-Check.
- **Audit-Log:** Append-only in Postgres. Admins sehen es in den Einstellungen. Aktionen des Support-Zugangs sind für den Kunden-Admin sichtbar.
- **Netzwerk:** DB- und Backend-Port nur auf `127.0.0.1` (bereits umgesetzt, Commit `fb20886`). Einziger öffentlicher Einstieg ist der Web-Port → Nginx → `/api`.

## Datenmodell (Migration `006_auth.js`)

Migration ist idempotent (`CREATE TABLE IF NOT EXISTS`, keine Seeds), weil ein Restore alter Backups den `migrations`-Stand bisher zurücksetzen konnte (siehe „Backup/Restore“).

| Tabelle | Wichtige Spalten |
|---|---|
| `users` | `id`, `email` (unique, lowercase), `name`, `password_hash`, `role` (`admin`/`user`), `is_operator` bool, `is_active` bool, `totp_secret_enc`, `totp_enabled_at`, `failed_login_count`, `locked_until`, `last_login_at`, `created_at`, `updated_at` |
| `user_recovery_codes` | `user_id`, `code_hash`, `used_at` |
| `sessions` | `id_hash` (PK, SHA-256 des Cookie-Werts), `user_id`, `created_at`, `last_seen_at`, `expires_at`, `ip`, `user_agent`, `mfa_pending` bool |
| `auth_tokens` | `token_hash` (PK), `kind` (`onboarding`/`invite`/`password_reset`), `user_id` nullable, `email` nullable, `role` nullable, `expires_at`, `used_at`, `created_by` |
| `rate_limits` | `key` (z. B. `login:ip:<ip>`, `login:user:<email>`), `window_start`, `count` |
| `audit_log` | `id` (bigserial), `at`, `user_id` nullable, `actor_label` (Name/E-Mail zum Zeitpunkt), `is_operator`, `action`, `entity_type`, `entity_id`, `details` jsonb, `ip`, `user_agent` |

- Alle Tokens (Session, Onboarding, Invite, Reset) mit 256 Bit aus `crypto.randomBytes`, in DB nur SHA-256-Hash.
- Passwörter: argon2id via `@node-rs/argon2` (Prebuilds für Alpine/musl, kein Build-Toolchain im Image).
- TOTP-Secret verschlüsselt mit AES-256-GCM, Schlüssel `AUTH_ENCRYPTION_KEY` (32 Byte, base64) in `.env.backend.<name>`, beim Deploy generiert. Fehlt der Key, verweigert das Backend den Start.
- `audit_log`: Trigger verhindert `UPDATE` und `DELETE` auf Einträge jünger als 90 Tage.

## Backend

### Middleware

- `requireAuth` global vor allen `/api/*`-Routen. **Whitelist** (ohne Login): `POST /api/auth/login`, `POST /api/auth/login/totp`, `GET/POST /api/auth/setup`, `GET/POST /api/auth/invite/:token`, `POST /api/auth/password-reset/request`, `GET/POST /api/auth/password-reset/:token`, `GET /health`. Neue Routen sind damit automatisch geschützt.
- `requireRole('admin')` für Einstellungs-Ressourcen (siehe Rechte-Matrix).
- Origin-Check für alle nicht-GET-Requests: `Origin` (oder `Referer`) muss zu `PUBLIC_URL` passen, sonst 403. Zusammen mit `SameSite=Lax` CSRF-Schutz.
- `cors()` (derzeit offen für alle Origins) wird entfernt; Frontend und API laufen same-origin.
- `app.set('trust proxy', …)`: Kette NPM → Frontend-Nginx → Backend. Anzahl Hops per `TRUST_PROXY_HOPS` (Default 2), damit Rate-Limit und Audit-Log die echte Client-IP sehen.
- Audit-Middleware: protokolliert jeden erfolgreichen schreibenden Request (`POST/PUT/PATCH/DELETE`, Status < 400) mit Methode, Route-Pattern, Entity-ID aus Params. Keine Request-Bodies (keine personenbezogenen Daten, keine PDFs im Log).

### Endpunkte `/api/auth`

| Methode | Pfad | Zweck |
|---|---|---|
| GET | `/setup?token=` | Prüft Onboarding-Token (gültig/abgelaufen/verbraucht) |
| POST | `/setup` | Token + Name, E-Mail, Passwort → erster Admin, Login. In Transaktion: nur wenn noch kein Nicht-Operator-Admin existiert (`SELECT … FOR UPDATE` bzw. Advisory-Lock) |
| POST | `/login` | E-Mail + Passwort. Bei aktiver 2FA → Session mit `mfa_pending`, Antwort `{ mfaRequired: true }` |
| POST | `/login/totp` | TOTP-Code oder Recovery-Code für `mfa_pending`-Session |
| POST | `/logout` | Session löschen |
| GET | `/me` | Aktueller Nutzer, Rolle, `isOperator`, 2FA-Status |
| POST | `/password` | Eigenes Passwort ändern (aktuelles Passwort nötig), beendet andere Sessions |
| POST | `/totp/setup` | `{ password }` erforderlich (Step-up); neues Secret + `otpauth://`-URI (QR im Frontend) |
| POST | `/totp/enable` | Code bestätigen → aktiviert, liefert Recovery-Codes einmalig |
| POST | `/totp/disable` | Passwort + aktueller Code nötig |
| POST | `/password-reset/request` | E-Mail → Mail mit Link. Antwort immer gleich (keine Account-Enumeration) |
| GET/POST | `/password-reset/:token` | Token prüfen / neues Passwort setzen, beendet alle Sessions des Nutzers. 2FA bleibt aktiv |
| GET/POST | `/invite/:token` | Einladung prüfen / Konto anlegen |

### Endpunkte `/api/users` (nur Admin)

| Methode | Pfad | Zweck |
|---|---|---|
| GET | `/` | Nutzerliste ohne Operator, plus `operator: { active, lastLoginAt }` |
| POST | `/invite` | E-Mail, Rolle → Einladungslink (+ Mail, falls SMTP) |
| PUT | `/:id` | Name, Rolle, aktiv/deaktiviert |
| POST | `/:id/password-reset-link` | Reset-Link erzeugen (Fallback ohne SMTP) |
| POST | `/:id/totp/reset` | 2FA eines Nutzers zurücksetzen (z. B. Gerät verloren) |
| DELETE | `/:id/sessions` | Alle Sessions des Nutzers beenden |
| POST | `/:id/unlock` | Sperre aufheben: `failed_login_count = 0`, `locked_until = NULL`, löscht die Login-Limits des Kontos (`login:user:<hash(email)>:*`) sowie `totp:user:<id>` und `pwchange:user:<id>`; Audit `user.unlocked`, 204. Passwort und Sessions bleiben unverändert |

Regeln: Operator ist über diese Endpunkte nicht änderbar (404). Der letzte aktive Nicht-Operator-Admin kann nicht deaktiviert oder herabgestuft werden. Nutzer werden deaktiviert, nicht gelöscht (Historie im Audit-Log bleibt zuordenbar). Deaktivieren beendet alle Sessions.

### Rechte-Matrix

| Bereich | user | admin |
|---|---|---|
| Kunden, Rechnungen, Angebote, Aufträge, Mahnungen, E-Mail-Versand, Reporting | lesen + schreiben | lesen + schreiben |
| `GET /api/company`, `GET` Stundensätze, Materialvorlagen, Plan | ✓ (für PDFs/Formulare nötig) | ✓ |
| `PUT /api/company`, Schreibzugriffe auf `hourly-rates`, `material-templates`, `yearly-invoice-start-numbers` | ✗ (403) | ✓ |
| `PUT /api/invoice-templates` (Rechnungsvorlagen aus dem Rechnungseditor; Body `{ invoiceTemplates: [...] }`, max. 200 Objekte, Spalte `company.invoice_templates`) | ✓ | ✓ |
| `email-management` SMTP-Einstellungen/Test/Diagnose | ✗ | ✓ |
| `email-management` Verlauf/Statistik | ✓ | ✓ |
| `backup` (alle Endpunkte inkl. Restore) | ✗ | ✓ |
| `users`, `audit-log` | ✗ | ✓ |

Die genaue Zuordnung pro Route wird bei der Umsetzung gegen die Einstellungsseite (`src/components/Settings*`) abgeglichen. Grundsatz: Was in den Einstellungen änderbar ist, ist admin-only.

### Rate-Limit und Sperre

- Login, TOTP, Reset-Request, Setup, Invite: **5 Fehlversuche / 15 min pro Account** und **20 / 15 min pro IP** → 429 mit deutscher Meldung und `Retry-After`.
- Login: Das harte 429-Limit pro Account gilt **pro Account+IP** (`login:user:<hash(email)>:<ip>`, 5 / 15 min), damit niemand allein mit einer bekannten E-Mail-Adresse (z. B. `support@openbills.de`) den Login des Kontos von anderen IPs blockieren kann. Daneben gilt das Limit pro IP (20 / 15 min). Bei Erfolg wird der Account+IP-Zähler gelöscht und der IP-Versuch freigegeben. TOTP (`totp:user:<id>`) und Passwortwechsel (`pwchange:user:<id>`) bleiben pro Account, da sie ein korrektes Passwort bzw. eine Session voraussetzen.
- Nach 10 Fehlversuchen in Folge (über alle IPs, `failed_login_count`): Account 15 min gesperrt (`locked_until`), Audit-Eintrag. Die Sperre blockiert nur **neue Logins** (423 nach korrektem Passwort); bestehende Sessions bleiben gültig. Ein Admin kann Sperre und Limits eines Nutzers vorzeitig aufheben (`POST /api/users/:id/unlock`, UI „Sperre aufheben“); `toPublicUser` liefert dafür `lockedUntil` (nur solange die Sperre läuft).
- Zähler in Postgres (`rate_limits`), damit Restarts sie nicht zurücksetzen. Alte Einträge räumt ein stündlicher Job ab.
- Login-Antworten sind identisch für „unbekannte E-Mail“ und „falsches Passwort“; bei unbekannter E-Mail wird trotzdem ein Dummy-Hash geprüft (Timing).

### Passwortregeln

Mindestens 12 Zeichen, max. 128. Kein Komplexitätszwang. Prüfung gegen eine kleine lokale Liste häufiger Passwörter. Kein externer Dienst.

### Audit-Log

Explizit protokolliert (zusätzlich zur generischen Schreib-Middleware):

- Auth: Login erfolgreich/fehlgeschlagen, Logout, Sperre, 2FA aktiviert/deaktiviert/zurückgesetzt, Recovery-Code verwendet, Passwort geändert, Reset angefordert/abgeschlossen
- Nutzer: Setup (erster Admin), Einladung erstellt/angenommen, Rolle geändert, deaktiviert/reaktiviert, Sessions beendet
- Betreiber: jeder Login des Support-Zugangs, Operator-Passwort zurückgesetzt (per Skript, `user_id` null, `actor_label` „System“)
- Daten: Backup erstellt/heruntergeladen/wiederhergestellt/gelöscht, Firmen- und SMTP-Einstellungen geändert, Rechnung/Angebot Statuswechsel, Löschungen

`GET /api/audit-log?from=&to=&userId=&action=&page=` (Admin), Ansicht in den Einstellungen mit Filter, CSV-Export.

**Aufbewahrung:** 90 Tage (inkl. IP-Adressen), danach löscht ein täglicher Job ältere Einträge. Frist als Konstante `AUDIT_RETENTION_DAYS = 90`; Anpassung später zusammen mit Landing/AVV.

## Skripte

### `deploy-instance.sh`

Neu abgefragt: **öffentliche URL** (z. B. `https://kunde.openbills.de`). Generiert `AUTH_ENCRYPTION_KEY`. Schreibt `PUBLIC_URL`, `AUTH_ENCRYPTION_KEY`, `TRUST_PROXY_HOPS` in `.env.backend.<name>`.

Nach erfolgreichem Start (Healthcheck abwarten):

1. `docker compose exec backend node scripts/operator.js reset` → legt Support-Zugang an (E-Mail `support@openbills.de`), generiert Passwort, gibt **E-Mail + Passwort einmalig** aus.
2. `docker compose exec backend node scripts/onboarding.js` → erzeugt Onboarding-Token (48 h), gibt `PUBLIC_URL/#setup/<token>` aus.

Ausgabe enthält den Hinweis, beides sofort in den Passwortmanager bzw. an den Kunden zu übergeben. Gilt für interaktiven und `--legacy`-Modus (dort URL als 6. Parameter).

### `manage-instances.sh`

- `onboarding-link <name>`: neuer Onboarding-Link. Alte, ungenutzte Onboarding-Tokens werden ungültig. Abbruch mit Meldung, wenn bereits ein Kunden-Admin existiert.
- `operator-reset <name>`: legt Support-Zugang an, falls er fehlt, sonst neues Passwort, beendet seine Sessions, setzt seine 2FA zurück. Gibt Credentials einmalig aus. Audit-Eintrag.
- `list` zeigt zusätzlich `PUBLIC_URL`.

## Frontend

- Neue Kontext-Datei `AuthContext` (`GET /api/auth/me` beim Start). Ohne Session → Login-Seite statt App.
- Neue Hash-Routen ohne Login: `#setup/<token>`, `#invite/<token>`, `#reset/<token>`, `#forgot-password` (bestehendes Hash-Format `#page/param`). `App.tsx` prüft diese vor dem Auth-Gate.
- `api.ts`: `credentials: 'same-origin'`; bei 401 → Login-Seite, bei 403 → Hinweis „Keine Berechtigung“.
- Nutzer-Menü: Name, Passwort ändern, 2FA einrichten, Abmelden.
- Rolle `user`: Navigationspunkt Einstellungen ausgeblendet. Die bestehenden Redirects nach `settings` bei deaktivierten Modulen (`App.tsx`) leiten für `user` aufs Dashboard.
- Einstellungen (Admin): neue Tabs **Nutzer** (Liste, Einladen, Rolle, Deaktivieren, Reset-Link, 2FA zurücksetzen, Hinweis Support-Zugang) und **Audit-Log**.
- Hinweisbanner für Admins ohne 2FA: „Zwei-Faktor-Authentifizierung wird empfohlen“, ausblendbar pro Sitzung.
- QR-Code für TOTP clientseitig (`qrcode`), Secret zusätzlich als Text.
- Alle Texte Deutsch.

Frontend-Gating ist UX; das Backend setzt alle Rechte durch.

## Backup/Restore

- Auth-Tabellen (`users`, `user_recovery_codes`, `sessions`, `auth_tokens`, `rate_limits`, `audit_log`) sind **nicht** Teil des App-Backups und werden beim Restore **nicht** angefasst. Keine Hashes/TOTP-Secrets in Backup-Dateien. Ein Backup lässt sich in jede Instanz einspielen, ohne Logins mitzunehmen.
- **Fix:** Restore lässt die Tabelle `migrations` aus. Bisher setzt der ZIP-Restore den Migrationsstand auf den des Backups zurück; beim nächsten Start würden neuere Migrationen erneut laufen. `migrations` wird nicht mehr mitgesichert.
- Umfang steht nur in `backend/utils/backupTables.js` (`BACKUP_TABLES`, `EXCLUDED_TABLES`); ein Test prüft, dass jede DB-Tabelle genau einer Liste zugeordnet ist.
- Nur noch ZIP-Backups (JSON-Backup entfernt). Daten liegen als `database.json.enc` im ZIP, verschlüsselt mit Backup-Passwort (AES-256-GCM, scrypt-Parameter in `encryption.json`, min. 12 Zeichen, nicht gespeichert). `metadata.json` bleibt lesbar (nur Zähler). Alte ZIPs mit `database.json` werden ohne Passwort wiederhergestellt.
- `smtp_settings.smtp_pass` liegt mit `AUTH_ENCRYPTION_KEY` verschlüsselt in der DB (Migration `008`). Im Backup steht es im Klartext (das Backup ist ja verschlüsselt), damit es in Instanzen mit anderem Schlüssel einspielbar ist; der Restore verschlüsselt neu.
- Nach dem Restore werden Serial-Sequenzen (`id`) auf `MAX(id)+1` gesetzt.
- Restore erzeugt einen Audit-Eintrag `backup.restored` mit Name der hochgeladenen Datei, Ersteller und `details.format: 'zip'`.
- Vollständige Wiederherstellung inkl. Nutzern: DB-Dump über `./manage-instances.sh backup` (bei Umsetzung prüfen, dass es ein vollständiger `pg_dump` ist).
- Bekannt: `usage_counters` ist nicht im App-Backup; nach Restore in eine neue Instanz startet der Monatszähler bei 0. Akzeptiert.

### Abläufe

**Neue Instanz + Restore (Umzug):** Deploy → mit Support-Zugang anmelden → Backup einspielen → Onboarding-Link an Kunden. Reihenfolge von Restore und Onboarding beliebig.

**Bestehende Instanz von Authentik umstellen (empfohlen in-place):**

1. Backup erstellen.
2. `PUBLIC_URL`, `AUTH_ENCRYPTION_KEY` in `.env.backend.<name>` ergänzen (`manage-instances.sh config`), `git pull`, `restart`. Migration legt leere Auth-Tabellen an, Fachdaten unverändert.
3. `operator-reset <name>`, `onboarding-link <name>` → Link an Kunden.
4. Authentik bleibt bis zum Abschluss des Onboardings vor der Instanz (doppelter Login). Danach Forward-Auth im NPM entfernen.

Zwischen Schritt 2 und Onboarding ist die API nicht offen: ohne Session 401, Anlegen nur mit gültigem Token.

## Abhängigkeiten (Backend)

- `@node-rs/argon2` (Passwort-Hashing)
- TOTP (RFC 6238, SHA-1, 6 Stellen, 30 s, ±1 Schritt Toleranz) mit `crypto` selbst implementiert (~40 Zeilen, testbar gegen RFC-Testvektoren); kein zusätzliches Paket.
- Cookies: `cookie-parser` oder manuelles Parsen des `Cookie`-Headers.
- Frontend: `qrcode`.

## Tests

- Backend (Vitest, neu über reine Contract-Tests hinaus): TOTP gegen RFC-6238-Vektoren, Token-Hashing/Ablauf, Rate-Limit-Logik, Rechte-Matrix (jede Route aus `server.js` ohne Session → 401, als `user` auf Admin-Routen → 403), Setup-Race (zwei parallele Setups → genau ein Admin), letzter Admin nicht deaktivierbar, Operator über `/api/users` nicht änderbar.
- Datenbanknahe Tests laufen gegen einen Postgres-Container.
- Frontend: Auth-Gate und Routen ohne Login.

## Nicht im Umfang

- SSO/OIDC (Authentik als optionaler Login-Provider) — später möglich.
- Feingranulare Rechte über `admin`/`user` hinaus.
- WebAuthn/Passkeys.
- Serverseitige Inhalts-Diffs im Audit-Log (welches Feld von was auf was).
